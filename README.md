## 第一次迭代

### 目标
  
  完成基本的数字加减乘方，以及未知数**x**的运算，以及识别到其中的 `(`。

### 基本思路

  第一步完全没有框架的时候是最难的，因为不知道怎么搭建起运算体系。但是只要能够想到构建一个**Mono**(单项式类)，以及**Poly**(多项式类)作为运算的核心，再加上**根据文法理解递归下降，表达式由项相加而成，项由因子相乘，而因为**^**号的需要两个因子，所以我特地准备了一个CellFactor,每次抓取因子时抓取一个因子和一个 `^`，如果抓到了 `^`就再抓取一个因子来组成一个CellFactor**。所以题目的关键还是抓取每一个Factor，之后转换成Poly来进行加减乘与乘方。
注意：

  + 在准备将解析表达式之前还要处理空格以及连续的加减号，所以建立了Process类来进行预处理。
  + 因为Factor的种类很多，所以将Factor设置为接口，将其他元素统统归为Factor，而因子能够参与计算的关键是将其转为Poly，所以为每一个Factor准备好toPoly这个方法。

评测的性能由总体长度决定，于是我选择做一些优化，但第一次作业我没有彻底优化，我先说第一次我优化了的点。

## 第二次迭代

### 目标

  加入了函数、选择因子，exp()指数函数。

### 基本思路
  
  架构上我沿用了第一次迭代的架构，总体差别不大，但是为了让新加的三个因子融入原来的架构，我作出如下部署：

  1. f(x):在第二次作业中我采用了字符串替换的方式(类似于宏替换)，也就是在Process里读到f(x)时，顺便将其替换为相应的函数。
  2. exp(x):exp(x)相对比较简单，在Mono中，原来的范式为：**系数，指数**，现在新加一个维度，**系数，指数，Poly**，Poly代表的是exp的指数部分。exp(x)的加入简单，但是后续处理相等的时候这里就是最难的，因为Mono和Poly现在开始有递归嵌套了。
  3. 选择因子：新建了一个因子，其创建方法为四个类，


```

  if (A==B) return C
  else return D
```

选择逻辑如上，但是如何判断两个**Poly**相等呢，所以就需要提出一个**Poly**的范式，我的处理办法为建立一个**standPoly**的方法，就是Poly总是按照一定的次序排列，为了实现standPoly这个方法，我新建了MonoExp这个内，并且重写了Hashcode用来给Poly进行排列，将所有的Poly处理成标准的范式，这样相同的Poly，其各个元素一定是相同的(这是第二次迭代最艰难的部分)。

为了适应新的要求，需要把Poly，Mono类进行重构，提供新的方法，但是框架不变，仍然递归下降，抓取因子，然后**toPoly**进行运算。


注意：嵌套函数的存在，可能会让指数变得很大，所以我的指数由**int**变成了**BigInteger**，否则会报错

### 优化

1. 时间也是性能的考虑之一，而在进行乘法运算时，由于函数可以嵌套，导致指数可以迭代到很大，这个时候我采取了快速幂运算。
2. 指数由**int**变到**BigInger**，数据强度更强

### 代码缺陷

1. 在解析函数时使用了宏替换的方式，这种方法实现简单，但拓展性特别差，破坏了函数作为一个因子的设定，（缺陷会在第三次迭代中体现出来，导致关于处理函数的部分需要全部重构）
2. standPoly在排序时花费时间很多，频繁调用standPoly这个方法浪费了大量CPU时间。
3. equal函数需要递归比较Poly与Mono，效率低，写错的话容易进入死循环。

## 第三次迭代

### 目标

  加入了求导因子(dx(),dy(),grad()),以及递推函数，y。

### 基本思路
  
  y:引入y和x一样，所以将计算方法中针对x的特性给y就可以了，将Mono范式中加上y的指数部分就可以了。
  求导因子：这个部分相对简单，新建一个因子类，按照求导规则，抓取一个因子与求导对象，然后在**Poly**与**Mono**内设计一个求导方法，依旧需要递归调用。

```
    dx(Poly) = dx(mono1+mono2+mono3……)
    dx(Mono) = xexponent*co*x^(exponent-1)*exp(Poly) + dx(Poly)*mono
```

  以x为例，求导方法需要递归调用,知道exp的Poly为**null**。
  递推函数：由于上一次我们的f(x)是宏替换处理的，现在已经不行了，递推需要将函数作为一个因子代入到这个计算当中。所以我们可以为Poly设计一个方法为xReplacement(因为定义的自变量只能是x)，将Poly中的x变为需要替换的**Poly**，再设计一个函数因子，这样就能解决函数代入计算的问题了。
  那么，如何解析函数在定义时的Poly，以及我怎么知道我的x要替换哪个多项式呢？

- 在这里我设计了一个函数登记表类(上帝视角替换Poly)，将所有普通函数以及递推函数在定义时 就解析为一个Poly存储到这个登记表上(注意这个登记表的所有属性都为static)，这样以后需要替换函数时就全局调用解析好的函数Poly。
- 在进行递推运算时有两种思路，一种是每次调用都使用递归去运算，但是这种比较浪费资源。因为递推函数的下标最多为5，所以我们完全可以把所有的函数计算好，存储在登记表里，这样在真实代入直接调用处理好的函数就可以了。我选用了第二种方法，因为第二种计算好后可以一劳永逸，在多次调用时能节省时间，但是数据点不需要多次调用的话也会浪费了资源。

### 优化

+ exp()函数可以提取公因子，使得长度变短，性能可以优化，但是有时候提取公因子长度反而会变长。于是我选择用时间换长度，比较提取公因子后的长度与提取前的长度，谁更短就用谁。 但是这样时间会变长。
+ 计算函数时不再使用宏替换，而是作为因子参与到parser中，架构拓展性更强，以后定义其他函数，只需往登记表里再登记函数即可。

### 代码缺陷

+ **dealResult**复杂度太高，由于我输出时不是按照范式进行的tostring输出，而是很多特判加处理输出，导致输出部分的代码逻辑混乱，容易出现bug，不稳定。
+ exp指数函数提取公因子，采用gcd算法，两两相比，复杂度过高，导致在hacker中被发现了破绽，被时间限制克制，成为代码败笔。
+ 递推函数处理特别复杂，我新建了三个类来进行递推换算，逻辑有点混乱，写到最后每个类分工不明确，相互耦合。

## 大模型辅助

我的代码百分之五是AI生成的。

1. debug，在第一次作业中由于我纯粹靠自己手写，而自己又未能及时发现bug，导致强测中失利未能进入互测，我痛定思痛，在提交前一定要让大模型检查一下bug，有很多bug虽然大模型未能发现，但是对于能过强测的数据点的bug大模型基本能应对，而且查找速度很快，一针见血，并提供解决bug的方法。
2. 辅助生成代码：比如我在进行快速幂时，这段代码我不会写，我问大模型，并且学习了这个算法。
3. 搭建评测机：可以让大模型搭建评测机，生成各种边缘以及有强度的数据点，对自己代码进行大规模的测试，而那些复杂的测试点自己去想的话需要花很多时间，但是大模型的评测机不是万能的，有很多刁钻的数据点需要结合代码分析给出痛点。
4. 对别人的代码进行hacker，既可以让生成的评测机去测试别人的代码，也可以让大模型辅助理解别人的处理逻辑，加入只靠自己去看别人的代码的话，花费的时间很多，而且可以专门针对别人的逻辑去生成数据点。

## 心得体会

这次系列的迭代让我递归下降有了深刻的认识，原来只需要理解一个文法就能将这个文法内的内容全部逮捕。以及设计类的优势，拥有一个核心的类(**Poly**)就能把所有的计算全部活起来，我之前才接触时完全不知道该怎么进行计算，但是把Poly以及各个Factor的toPoly维护好就能把所有的计算掌握，而且加入自己搭建的框架够硬，在扩展上将会有很多优势，所以一定要考虑扩展性，不要有太多特判。

我个人认为这三次难度徘行：第一次>第二次>第三次，因为第一次什么也没有，自己的框架也没有，完全不知道从哪里入手，所以基本每天都在想是怎么计算的，第二次需要对第一次的架构进行大改，所以工作量也很大，第三则是在原来的架构里添加东西，工作量相对较少。

但是第一次作业的失利，以及我第二三次作业加入了AI的辅助后成功了以及AI的优化算法的理解，我真的感受到了AI的强大，为自己纯粹的代码水平感到深深忧虑，对未来感到忧虑。

和室友以及同学讨论思路，一起hacker以及搭评测机、找bug是一种很神奇的体验，特别是看到自己的代码成功跑起来将数据运行起来的时候会很有成就感。
